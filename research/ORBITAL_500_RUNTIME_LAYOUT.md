## What the confirmed official 5.00 system PUP can supply

The PUP at `firmware/official/PS4UPDATE-5.00-system.PUP` is the 374,669,312-byte **system/update PUP**. Orbital's own `bin/hdd/README.md` says `eap.img`, `system.img`, and `system_ex.img` are extracted from a normal **or** recovery PUP matching the target version. Therefore those three partition images are derivable from this PUP after the historical on-console PUP-decryption step and the documented host unpacking step. The source PUP is encrypted/signed; the checked-in unpacker only unpacks already-decrypted PUP blobs. No extraction/decryption has been performed here.

The README says `preinst.img` and `recovery.img` must come from a recovery PUP, and calls them version-invariant. This system/update PUP is not that recovery PUP, so it does not satisfy those inputs. The USB image `usb/usb-pup-500rec.qcow2` is also explicitly a recovery image in the historical runner name. Orbital does not document its image-construction recipe or a way to generate it from the system/update PUP.

The fact that the PUP may contain firmware components does not establish that it supplies Orbital's separate `sflash/orbisys-500`, `sflash.bin`, or `vbios.bin`: the historical tree documents those as decrypted kernel/SFLASH/VBIOS inputs, and does not document a PUP-to-these-files extraction process. Treat them as console dump inputs unless a source-backed, legitimate extraction route is established. SAMU blobs are generated by Orbital Dumper from console runtime inputs; the official PUP alone cannot produce the required decrypted blob archive. The PUP does contain filesystem content from which userland files may be extracted after decryption/unpacking, but the repository does not specify the exact decrypted executable set needed for Safe Mode; Orbital's manual points to Orbital Dumper and says its decrypted files go in `bin`.

The historical decryption workflow is: run `ps4-pup_decrypt` on the PS4 to create decrypted PUP blob files, then run `ps4-pup_unpack` on the computer. The official 5.00 system PUP can therefore support preparation of the matching system partition images once the owner performs that console step. The user-provided PUP is **not missing**; the downstream decrypted outputs are not yet present.

It reports the source-level distinction above rather than claiming the three unreferenced images are read by this revision. The user guide says to decrypt a PUP on the console with `ps4-pup_decrypt` and unpack it on the computer with `ps4-pup_unpack`; these are optional open-source tools, not supplied here. No Sony PUP is downloaded or included.

## Crypto blob production and decrypted userland files

Orbital Dumper emits decrypted blob data as `<uppercase-MD5>.bin` files under its dump output (`tools/dumper/source/blob.c` and `tools/dumper/server.py`). QEMU does not read loose `.bin` files: it opens `crypto/blobs.zip` and searches its root entries using the MD5 of the encrypted bytes it encounters. ZIP structure and decompression can be checked locally; correspondence to encrypted proprietary inputs cannot be proven by the preflight without the same encrypted inputs, and it is not guessed.

The historical Windows manual says decrypted userland executables are produced by Orbital Dumper and placed in `bin`. Its runner has no explicit per-executable command-line option. The pinned boot config loads the kernel, then the kernel accesses the mounted system images and invokes guest paths. The historical roadmap names `/mini-syscore.elf` and later `/system/sys/SceSysCore.elf`, but this is not a complete input manifest. No source-level static list was found that proves which decrypted userland ELF/SELF/SPRX files the Safe Mode path will request. Consequently the launcher/preflight can validate the disk and blob containers, but cannot certify complete Safe Mode userland coverage before a guest run.

## Open-source build outputs (not Sony firmware)

The 5.00 configuration uses `ubios.bin` and `boot.img` from the open-source Orbital BIOS and GRUB components. The historical QEMU command line then launches `qemu-system-ps4`, opens the system HDD and recovery USB image, selects eight virtual CPUs, the Orbital display, and an interactive stdio monitor. The QEMU process working directory must be the staging directory because several firmware paths are hard-coded relative paths.

`sflash/orbisys-500`, `sflash.bin`, `vbios.bin`, partition images, recovery USB image, and crypto blobs must come from legitimately owned user material. Build products, manifests, logs, and research remain outside any Git source tree.
